  ✦ 好问题。让我直接回答：

    cast_rays_parallel 不是多进程，是多线程

    关键代码在 lidar_point_cloud.py 第 166-178 行：

     1 with ThreadPoolExecutor(max_workers=num_batches) as executor:
     2     futures = {
     3         executor.submit(self._cast_rays_batch, model, data_copies[i], indices): i
     4         for i, indices in enumerate(batch_indices)
     5     }

    这里使用的是 concurrent.futures.ThreadPoolExecutor，即线程池，不是多进程（ProcessPoolExecutor）。

    self._lidar_front_num_batches 能设大于 32 吗？

    技术上可以，但不建议，原因如下：

    1. Python GIL 限制
    MuJoCo 的 mj_multiRay 是 C 扩展，在调用 C 代码时会释放 GIL，所以多线程确实能获得并行加速。但每个线程的 Python 层 overhead（如 numpy 数组操作）仍然受 GIL 串行化。

    2. 边际收益递减
     - 32 核 → 最多 32 个线程能真正并行
     - 设 num_batches=64 意味着 64 个线程争抢 32 核，上下文切换反而增加开销
     - 每个批次需要独立创建 MjData 副本（mj_forward 也有计算成本）

    3. 当前代码的实际并行度
    前向 LiDAR 720×96 = 69,120 射线，设 num_batches=16 时每批 ~4,320 射线。如果设 num_batches=64，每批仅 ~1,080 射线，批次过小会导致并行 overhead 占比增大。

    建议配置


    ┌──────────┬──────────────┬──────────────┬──────────────────────────────────────┐
    │ CPU 核数 │ 前向 batches │ 后向 batches │ 说明                                 │
    ├──────────┼──────────────┼──────────────┼──────────────────────────────────────┤
    │ 32       │ 16           │ 8-16         │ 前后 LiDAR 各占一半核，避免资源争抢  │
    ├──────────┼──────────────┼──────────────┼──────────────────────────────────────┤
    │ 32       │ 32           │ 1            │ 极端情况：前向独占所有核，后向单线程 │
    └──────────┴──────────────┴──────────────┴──────────────────────────────────────┘


    推荐 `self._lidar_front_num_batches = 16`（当前值），后向也保持 16 即可。设大于 32 不会有额外收益，反而可能变慢。
